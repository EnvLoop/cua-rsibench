It records zero new 19/20/100 controls, zero model attempts and zero official admissions before dispatch. The controller never imports Tinker or a researcher model. Although known-answer evaluator actions are saved privately for provenance, selection and final controls never produce SFT examples.

For each ID, the original-software runner acquires its partition's exclusive worker lease, writes an append-only hash-chained `case_started` event, creates a new mode-0700 attempt directory and persists an immutable task/source intent **before** any Docker or GUI action. It cold-restores PostgreSQL and the physical filestore; confirms an unsolved SELECT-only baseline; observes the source in the original Odoo browser; and performs a known-answer positive through fresh v0.6.6 screenshots/actions. After browser reload it saves raw SQL state, protected source filestore bytes and attachment store paths. It then changes one different business object through the same GUI grammar, reloads, saves the negative state and cold-restores the worker again. Every action frame, normalized pre-dispatch intent, applied receipt and bounded pre-intent stale-frame rejection remains private. A GUI action is never replayed after its intent.

The [independent auditor](../tools/odoo_v066_scale_audit_v1.py) reopens each immutable attempt, action/result chain, raw PNG, original task package and checkpoint. It recomputes baseline reward 0, positive reward 1 with no unintended-change code, and wrong-object reward 0 with exactly the family-specific negative code from the saved SELECT-only SQL snapshots and private gold. It checks complete physical filestore equality **before** web restart, protected source bytes **after** restart, and exact restored SQL. Only then can the controller append `case_completed`. The report distinguishes raw semantic qualification from visual source review; no case can be promoted into an official final denominator solely from these controls.

`run --max-cases N` processes at most N consecutive IDs. A later `--resume` verifies the hash chain, every completed case's raw receipt and its independent audit before touching the next ID. A dangling `case_started`, a `case_failed`, an unexpected attempt directory, a changed source byte or an inexact reset stops the lane for manual reconciliation. There is **no automatic replay or case substitution**. The first bounded live step, when another self-hosted lane is idle, is one case in each split; the same frozen plan can then continue toward 19/20/100. Any failure must retain its original directory and receive an explicit pre-result recovery amendment before a fresh attempt.

These are evaluator GUI solvability controls in real original Odoo Community software with synthetic operational fixtures, not student scores or recursive improvement results. Current fresh controls outside the accepted pilot: **train 0/19, selection 0/20, hidden-final candidates 0/100**. Official final tasks, researcher campaigns and model outcomes remain **zero**.
