# Remote original-software execution and local disk release

**Decision record, 2026-09-29. Status: design and read-only inventory only.** No remote benchmark VM has been provisioned, no application state has been uploaded under this plan, and no local benchmark VM may be removed on the strength of this document. The full-study admission, campaign, and final-result gates in the [preregistration](FULL_STUDY_PREREGISTRATION.md) remain unchanged.

## Why an image registry is insufficient

The original GitLab CE, Odoo Community, and Magento admin cells run inside local `linux/arm64` Colima Docker engines. The active GitLab profile is configured for 3 vCPU, 6 GiB RAM, and 24 GiB disk; the shared Odoo/Magento profile is configured for 4 vCPU, 6 GiB RAM, and 30 GiB disk. A read-only host measurement found approximately 9.3 GiB and 22 GiB allocated by their respective sparse data disks at this date. These measured allocations, rather than the nominal 54 GiB capacity sum, are the potential immediate disk recovery from retiring both profiles after verified migration. They can change as the worlds run.

An OCI registry such as [GitHub Container Registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry) stores images. It does not run Compose, preserve a running database, or transfer Docker volumes. The GitLab image is already pinned at `gitlab/gitlab-ce:18.5.0-ce.0` and its pulled image is `linux/arm64`; its evaluator reset also relies on a separate VM-local overlayfs seed and disposable upper directories. [Odoo's Compose file](../enterprise_fallback/odoo18/compose.yaml) pins the PostgreSQL and Odoo image digests but stores database and filestore in distinct named volumes. Magento's application/image and fixture/reset state likewise require a source-bound restore. Publishing any application image must exclude account credentials, private task identities, gold, traces, and saved-state data. A logged-in `gh` CLI does not by itself establish `write:packages` permission for GHCR; package permissions are a separate GitHub gate.

**Decision:** use one fresh ARM64 Docker VM first for a controlled migration; choose an actually orderable CAX31 if available, otherwise size and quote an EC2 Graviton host in the user's account. The minimum proposal is 8 vCPU, 16 GiB RAM, and 160 GiB SSD for serialized cells. For sustained full-study work and both existing worlds at once, prefer 8 vCPU, 32 GiB RAM, and at least 200 GiB SSD. This is a capacity hypothesis, not a throughput result. A small 0.5 GiB VM cannot host even one existing 6 GiB Colima world. An x86 VM would require explicit multi-architecture image proof and fresh native-GUI qualification rather than assuming the ARM64 environment transfers unchanged.

## Migration and release gate

1. **Inventory and quiesce each cell separately.** Record image digests and architectures, Compose/configuration hashes, Docker volume and bind-mount inventories, runtime versions, baseline saved-state manifests, and current controller/worker leases. Stop only the cell being snapshotted; preserve incomplete attempts and cost journals. Compute a source-bound SHA-256 manifest before transfer. The original local VM remains the recovery source.
2. **Create two independent recovery paths.** Store a private, encrypted, hash-verified cold archive of each VM data disk outside the Mac, and separately create application-native consistent backups. GitLab's [Docker backup guidance](https://docs.gitlab.com/install/docker/backup/) requires application data plus configuration and secrets; a GitLab backup must be restored to the [same edition and version](https://docs.gitlab.com/administration/backup_restore/backup_gitlab/). Preserve the overlayfs lower seed and verify its mount/copy semantics separately. For Odoo, snapshot the paired PostgreSQL database and physical filestore at the same stopped-state boundary. The registry receives images only. Keep decryption material separately recoverable; an object existing in a bucket is not a restore test.
3. **Build the remote runtime from pinned sources.** Install Docker Engine/Compose on an ARM64 Linux host, pull or build each image by immutable digest, recreate exact data paths and access modes, then restore one cell at a time. Use [Docker's SSH-backed context](https://docs.docker.com/engine/security/protect-access/) or a private tunnel for operator access, and keep the Docker daemon and native application ports off the public internet. Keep the hidden verifier, gold, and evaluator credentials outside the researcher/container namespace. The model's GUI view must still come from the original software, with the frozen screenshot/action protocol.
4. **Prove equivalence before admission.** For each restored cell, an independent process must reopen the complete baseline state and source hashes; run a native GUI known-positive and plausible wrong-object negative; verify saved database/files/artifacts and unrelated-state invariants; and perform an exact fresh reset, including GitLab's overlay and Odoo's filestore. Check screenshot geometry, timing, browser/API origin, ACLs, action guards, and host-specific paths. A host change requires a dated pre-result runtime amendment and fresh source-bound per-ID controls before any final-task admission. Historical local controls remain evidence but do not become remote official scores.
5. **Release local space only after a restore drill.** Reopen and decrypt at least one archived copy independently, check its complete SHA-256 manifest, inspect remote application health and all qualification receipts, verify no active local lease or process depends on the profile, and retain a second recovery path. Then retire one local Colima profile at a time and measure actual free-space gain. If any check fails, keep the local VM and report the failed step; do not silently repeat a benchmark attempt.

This plan moves the self-hosted original-software cells only. E2B Desktop already executes remotely, while Excel/PowerPoint in Microsoft web applications depend on their own account and isolation arrangements. The benchmark's Harbor evaluation harness is not a replacement for persistent Docker compute; the full English report cannot count an environment migration as a model result.
