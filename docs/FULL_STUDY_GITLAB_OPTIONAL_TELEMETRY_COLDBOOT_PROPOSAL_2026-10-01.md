# Optional telemetry cold-boot proposal

The retained index 9 child completed three GUI saves before failing in its third cold reset. Raw startup logs show `sv restart` timing out on `gitlab-exporter/log`, followed by Cinc reconfigure failure and container exit 1. Docker State reports OOMKilled false. The saved positive/partial/repeated-positive receipts contain 1/0/1, and full Git sidecars are present; the third original reset, case completion and trio are absent. Separate cleanup returned the exact baseline at generation 32. This identifies the failed stage and proximate service error, not a proven memory, PID, FIFO or supervisor root cause. The stopped spectator did not establish robust startup. No historical failure is promoted or replayed.

Use one documented optional-telemetry profile for every later control and student container, after neutral validation. [GitLab's constrained-environment guidance](https://docs.gitlab.com/omnibus/settings/memory_constrained_envs/#disable-monitoring) permits removing optional monitoring. The pinned [18.5 Prometheus parser](https://gitlab.com/gitlab-org/omnibus-gitlab/-/raw/18.5.0%2Bce.0/files/gitlab-cookbooks/monitoring/libraries/prometheus.rb) disables the monitoring group; the [18.5 service map](https://gitlab.com/gitlab-org/omnibus-gitlab/-/raw/18.5.0%2Bce.0/files/gitlab-cookbooks/package/libraries/config/services.rb) identifies six CE services: node exporter, GitLab exporter, Redis exporter, Prometheus, Alertmanager and PostgreSQL exporter. PostgreSQL, Redis, Gitaly, Puma, Sidekiq, Workhorse, nginx, KAS and logrotate remain outside that group.

The fixed settings disable those six monitoring services and their aggregate monitoring switch, plus only Puma exporter and Sidekiq metrics endpoints. Explicit service settings prevent an inherited user override from leaving an exporter enabled; the [pinned settings precedence](https://gitlab.com/gitlab-org/omnibus-gitlab/-/raw/18.5.0%2Bce.0/files/gitlab-cookbooks/package/libraries/helpers/services_helper.rb) gives user settings priority over computed defaults. This does not change worker counts, concurrency, database configuration, authentication, grading, task state, waits or restart policy. No admin UI metrics setting or database row is changed.

`gitlab_world/v066_optional_telemetry_profile_v1.py` renders only that fixed suffix. It never operates Docker, deletes a file, starts a task or changes a seed. Its environment renderer preserves all existing unrelated entries and SVWAIT60. The [Docker configuration documentation](https://docs.gitlab.com/install/docker/configuration/#pre-configure-docker-container) states that environment settings load before `gitlab.rb` and are not retained across run commands. Accordingly, put the same suffix at the end of the fresh clone's upper-backed `gitlab.rb` and in each generated container environment. Retain both input/output hashes privately. Never modify the immutable lower config, logs or data seeds. Do not apply a global `disable all services` operation or the broader documented KAS/Puma/concurrency optimizations.

Before consuming another task identity, the root should execute exactly three neutral fresh cold-clone cycles under this one profile:

1. Verify there is no active GitLab lease, supervisor or actor. Preserve the terminal journals and current exact baseline. Pause the unused active container to provide the same fixed host resources for the neutral trial.
2. Create a uniquely owned neutral COW clone from the existing immutable 33-project seed, with fresh upper/work paths. Use the same image, baseline, source cores, operator data and SVWAIT60/readiness900/action720/supervisor7200 bounds. Apply only the optional telemetry suffix to this clone's config upper and private environment. Do not consume a task or copy any old task-completion marker.
3. Boot once with zero automatic restart attempts. Retain startup logs and limited State, effective false settings, native service status and the complete independent 33-project SQL/Git snapshot. The six exporters must be disabled or absent; the seven critical services must be running; saved state must equal the exact baseline.
4. Stop and remove only the owned neutral container, then verify its absence and teardown of its owned overlay mounts. Retain teardown command/status proof and immutable seed/source/core metadata before/after. Repeat with another distinct container identity for cycles two and three. A failure terminates the neutral trial; preserve it and do not start a task batch.

This is a finite root-executed neutral experiment, not an additional task or source-family continuation namespace. The source-only validator checks the three declared cycle readbacks and rejects critical-service loss, seed/data change, reused identities, added retries or missing teardown evidence. Actual root review must independently reopen the bound raw files; its field checks alone are not native proof. Only after successful cold boots and teardown should a uniform runtime amendment and fresh task-range decision be considered. The frozen image and task/grader/source cores remain identical, while the operational configuration changes explicitly and applies equally to every model and control.

No ephemeral PID/FIFO deletion is proposed: the retained failure lacks the file-type, ownership, PID/liveness and seed-vs-upper evidence needed to identify such state safely. [Pinned runit helpers](https://gitlab.com/gitlab-org/omnibus-gitlab/-/raw/18.5.0%2Bce.0/files/gitlab-cookbooks/runit/libraries/helpers.rb) show the logger restart/force-reload calls, but do not prove that copied supervision state caused this failure. The optional-monitoring change removes the observed optional startup branch; it is not a guarantee that another service cannot fail. Native neutral validation is pending. Model, provider, task-dispatch and official grading credit remain zero for this proposal.
