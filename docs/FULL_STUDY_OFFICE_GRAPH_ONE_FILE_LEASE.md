# Evaluator-only Office Graph one-file permission lease

**Status: protocol implementation, not a live account acceptance result.** No Microsoft Graph write, browser action, E2B lease, or model call was dispatched while building this controller. The repository ships no valid personal-account capability receipt, owner/actor Graph token, six-cell ratification, or qualified final-task lease. Current official campaign and final-result counts remain zero.

`tools/office_graph_one_file_lease_v1.py` leases one exact owner-drive file to one distinct actor account for an original PowerPoint or Excel **training** task. Its private specification binds cell and split, task package, source-seed and action-profile hashes, exact owner/actor Graph IDs and emails, drive/item/parent/sentinel IDs, file name, a hash-checked item-source readback, and a short-lived capability receipt from a **separate train-only account pilot**. Before a write, owner and actor delegated tokens are checked against `/me`; the owner drive must report `driveType: personal` and the expected owner; the target must be a non-root item under the expected parent; owner item/parent permissions must have no actor or broad/unknown direct grant; and the actor must be denied the target, parent and sentinel. A missing or changed receipt fails before POST. The same API design can serve future selection/final tasks, but this implementation refuses those splits until their separate frozen-matrix/task-admission gate is wired; a train pilot cannot authorize exposure of hidden items.

The evaluator then writes a mode-0600 hash-chained **invite intent and exact request bytes before one Graph POST**. The request names one actor recipient, `roles:["write"]`, `requireSignIn:true`, and `sendInvitation:false`. A valid 200 response must contain exactly one direct, specific-person write permission with a nonempty ID and no link or inheritance. That ID stays private. Owner permission readback must show exactly that grant; an evaluator-held actor token must read the assigned item and still fail to read the parent and sentinel. The actor model receives no Graph tool or bearer token and continues to edit only through Office GUI.

Deletion writes an exact-ID DELETE intent before sending it. A 204 response is followed by owner effective-permission readback and actor denial. The old permission ID, actor identity, anonymous/organization or unidentified links, and unknown direct grants are rejected; owner and unrelated inherited entries are allowed. This reflects Microsoft's documented [effective permission list](https://learn.microsoft.com/en-us/graph/api/driveitem-list-permissions?view=graph-rest-1.0), which need not become empty after removing one actor grant. A timeout or process death after either write leaves the journal uncertain. Reconciliation performs **GETs only**: it may adopt one uniquely observed actor grant or confirm the exact grant is absent and the actor denied. It never replays POST or DELETE automatically. The first attempt, request hash, response classification, ID hash, and every recovery observation remain in the private journal.

The API shape follows the official Microsoft Graph v1.0 [driveItem invite](https://learn.microsoft.com/en-us/graph/api/driveitem-invite?view=graph-rest-1.0), [permission DELETE](https://learn.microsoft.com/en-us/graph/api/permission-delete?view=graph-rest-1.0), and [permission resource](https://learn.microsoft.com/en-us/graph/api/resources/permission?view=graph-rest-1.0) documentation. Those docs list delegated personal `Files.ReadWrite` for invite/delete on non-root driveItems and permit `sendInvitation:false`. They do **not** prove that this particular personal OneDrive account can silently grant the actor, that the resulting invitation facet has the exact expected fields, or that the actor can access a shared owner's item through `/drives/{drive-id}/items/{item-id}`. All three must pass the bounded train-only pilot before a capability receipt may be frozen. The controller intentionally refuses a 207 partial response, multiple grants, an unredeemed/opaque actor identity, changed owner, absent permission ID, broad link, or any unknown state.

The controller does not create workbook/deck files, score tasks, authenticate the Office browser, or settle provider charges. It is an evaluator permission boundary that must be paired with source-bound item provisioning, the existing Office GUI actor/owner-download workers, and the full-study all-in budget ledger before dispatch. The short-lived capability receipt is a local evaluator assertion with referenced pilot evidence, not a cryptographic Microsoft attestation; reviewers must inspect the underlying authenticated pilot trace. Unattended Office actor sign-in remains a separate publication-scale blocker even if owner-side permission leasing works.

Offline fake-transport tests cover exact invite/readback/delete, owner and inherited permissions, actor target/sentinel isolation, missing account capability, wrong owner, broad links, 207 ambiguity, lost POST/DELETE responses, process death after intent, no automatic replay, journal tampering, and private permission-ID tampering. None is a live OneDrive acceptance test. Context7's quota was exhausted, so the implementation was checked against the linked Microsoft primary documentation and the repository's pinned Graph readback behavior.
