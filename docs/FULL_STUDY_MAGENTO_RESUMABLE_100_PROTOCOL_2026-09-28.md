# Pre-result Magento 100-case resume and infrastructure retry protocol — 2026-09-28

**Status: prospective execution rule, not a result.** The cron-free training gate and its private v1 freeze precede this amendment. No revised final-candidate GUI control, model attempt, or official admission is credited by the amendment. The original v1 freeze and its published hash remain method history. A new private v2 freeze must be generated and its hash recorded in the dated public receipt **before** the first revised candidate control; commit and publish that receipt before dispatch. The runner refuses a missing or changed public receipt. The v2 freeze binds the original freeze hash and runtime fingerprint, unchanged 100-case plan bytes and ordered task/package identities, source commit, original GUI runner/auditor bytes, and this resume/audit implementation. An old v1 freeze alone does not authorize the new runner. A code, plan, source, or runtime change after v2 freeze invalidates dispatch and requires a new pre-result revision.

The 100 distinct final-candidate IDs remain in their frozen order. Each task receives two fresh, no-mount Magento application/search pairs: native GUI positive save with independent persisted-state score **1**, then a separate cold reset with native GUI wrong-variant score **0**. Both exact pairs are cleaned. Every attempt and private diagnostic stays under ignored `work/`; public outputs contain only aggregates and hashes. Historical 35 controls and the two earlier index-drift failures are not pooled with this revised runtime. These controls make the evaluator eligible for individual task admission; they are not model outcomes or final admissions.

The runner writes a sequence-numbered, hash-linked, append-only journal before each attempt and after every process, pair cleanup, and completed task. One attempt occupies a separate immutable directory. On host sleep, process death, or observation interruption, resuming reads the original directory and the same frozen contract. A task with a completed calibration, both cleanup events, saved positive/negative readbacks, and a material reset is adopted once without running it again. A partly executed task is never resumed mid-pair. It stops pending a read-only infrastructure audit and exact cleanup; later task IDs cannot start early. The operator retains the original stopped attempt, including stdout/stderr and process receipts.

At most **one entire fresh-case retry per task ID** and **20 infrastructure retries across the 100 IDs** are permitted. The 20-case cap is fixed before any revised candidate result. The historical original-runtime workflow encountered roughly three interruptions over 35 controls; 100 cases require 200 fresh pairs plus 60-second idle checks, so a cap of eight would have a substantial chance of stopping a methodologically valid cell due to infrastructure alone. Twenty permits recovery while still capping invalid attempts at 20% of distinct IDs. The final aggregate must report both the invalid-attempt count and the cap; it must not hide attempts or select replacement/easier IDs. A second invalid attempt for any ID, the 21st infrastructure retry, or a deterministic task failure stops the cell for a separate prospective decision.

Only an unfinished **non-GUI** step, an unambiguous host/process gap, or two specifically identified native CMS navigation timeouts **before any edit** may be classified as invalid infrastructure. The menu exception requires the retained 60-second `item-edit` visibility timeout; the page-title exception requires the retained 120-second `locator("h1.page-title")` wait timeout. Each needs a matching process/stderr hash, the saved pre-neutral snapshot, no neutral `private-after` or result, no later GUI intent, and live material-state equality to its saved before snapshot. A different nonzero completed process, positive saved-state score other than 1, wrong-variant score other than 0, failed material reset, changed source/index, missing frozen preparation, unreceipted live container, or any verifier disagreement is **not** retryable under this rule.

An interrupted positive/negative GUI subprocess with no completed result is eligible only if the exact driver process is terminal, neither saved result nor post-action snapshot exists, and **two independent live readbacks** of the entire monitored SQL/search state exactly equal the normalized pre-GUI baseline. The frozen cron configuration and derived-price index must still match, and the exact no-mount pair must be retired. Any changed or uncertain state, live driver, missing baseline, or completed nonzero GUI process stops the cell. A successful GUI step may precede a later non-GUI interruption only when its independent result and current saved state still match. Before authorizing one whole-case retry, the separate read-only audit binds the current pair to the exact prepared container IDs, pinned images and zero mounts, and verifies the material SQL/search state against the last immutable snapshot. If no pair is active, both reserved container names must be absent. Cleanup records an intent before each exact `stop` and `rm`, verifies identity again, and can reconcile an interrupted cleanup using those intents. The audit, cleanup intent, cleanup receipt, and retry event are all retained. The retry starts two **new** pairs and repeats the full positive/negative/reset contract; no positive from the failed attempt is reused.

**Preseed container edge, registered before launch.** A preparation may stop before writing its preparation receipt. If both disposable containers remain **running**, no task-seed intent exists, and their pinned images, zero mounts, names and creation timestamps bind to the exact preparation intent, the evaluator may perform a read-only adoption audit. That audit must prove zero quote pages, the unchanged 181-document source search digest, the frozen cron configuration, 8,156 derived-price rows with zero drift, matching replica/live price hashes, and the exact container IDs; it retains hashes of Docker inspect and logs. The same material fields must still match immediately before exact-ID cleanup and one whole-case retry. A missing, partial, or **exited** pair cannot provide live SQL/search equivalence; the evaluator records the failure and stops this v2 cell for a separately dated prospective method decision. It does not start an exited container to manufacture a passing audit or infer equivalence from logs alone.

The final audit requires exactly 100 ordered distinct completed cases and 100 fresh positive/negative/reset proofs under the v2 freeze. It independently validates the v1 cron-free preparation and exact runtime identities in each successful pair, the bounded retry receipts, and the private journal. Only then may it emit a public aggregate. Any partial, tampered, duplicate, or mismatched journal emits no success receipt. The audit reports zero model calls and zero official final admissions. Model evaluation, 24 researcher campaigns, individual admission, and publication of full-study results are separate later gates.

The private operator sequence is: create the v2 freeze once with `--public-out docs/evidence/magento-resumable-100-freeze-2026-09-28.json`, commit and publish that aggregate receipt, then run the new campaign; on a stopped candidate, invoke `reconcile --mode audit`, inspect its private evidence, then invoke `reconcile --mode cleanup` only if the strict classifier accepts it; invoke `run --resume` with the **same** campaign directory. Repeat only within the fixed limits. The `audit` action is allowed only after all 100 controls complete. All actions are implemented in [`tools/magento_resumable_100_v2.py`](../tools/magento_resumable_100_v2.py); no live candidate control was run while authoring this rule.
