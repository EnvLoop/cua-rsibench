# Ordered shutdown for the neutral GitLab trial

V3 ended before creating a clone. The Docker stop command returned 0, but the preserved container process exited 1. The saved window shows PostgreSQL and Redis stopping before Sidekiq finished draining, followed by `timeout: run: sidekiq`, which wanted down and had received TERM. The installed `/assets/init-container` uses `set -e`; its SIGTERM trap calls `gitlab-ctl stop`. The aggregate stop failure therefore propagates to PID 1. The installed entrypoint SHA is `e1b4ea81d84147a5eb10c13d53d9cb82a721bc0f5b21b0b2b9daa3fd24526a0d`. V3 remains a failed, consumed attempt. Its 238 native bindings, cleanup and exact restoration have been verified without changing the failed outcome.

V4 proposes a dependency-preserving shutdown order. Only after the existing zero-worker/exclusive-lock proof and original baseline readback, stop Sidekiq while PostgreSQL and Redis still run. Confirm Sidekiq is down and both dependencies remain up, then call the unchanged Docker stop with its existing 300-second allowance and strict process-exit-0 requirement. Use the same order for every owned clone teardown. This targets the observed shutdown failure; native success remains unproven until the fresh three-cycle trial completes. The command is supported by [GitLab's service-specific maintenance guidance](https://docs.gitlab.com/update/package/package_troubleshooting/) and [Docker restore guidance](https://docs.gitlab.com/administration/backup_restore/restore_gitlab/).

Actor/runtime service configuration is unchanged. Sidekiq is stopped only during the reviewed lifecycle of unused instances, with its dependencies available. No critical service is disabled, no force kill is introduced, and SVWAIT 60, readiness 900, stop 300, image, hardware, concurrency, KAS, telemetry suffix, seeds and task data remain unchanged. There are no startup retries. If a targeted original stop fails before Docker stops, restoration may start that deliberately stopped Sidekiq once and then verifies all seven critical services. That is rollback of the lifecycle action, not a second trial or error credit.

The native service-status reader retains stdout, stderr and exit code. Installed omnibus-ctl source sums individual runit command exit statuses. Exit 1 is accepted only for a parsed, known down service with no stderr error; it is never called healthy. Exit 0 still requires valid known run/down rows. Daemon/context errors, malformed or unknown statuses, empty output, unrecognized services and other codes fail. The shared `disabled` receipt label means a down runit process in this reader, not a configuration change. A failed ordering step still attempts the frozen owned teardown; the original restoration remains in its unconditional exit path.

Every targeted stop has independent before/after status streams, a command reference, and a proof that PostgreSQL and Redis stayed running. The saved auditor reopens those bytes and checks the exact scoped container command. Owned process exit state is retained before removal; a nonzero exit remains failed even if cleanup succeeds. Original restoration includes a new raw critical-service readback.

The native node reader now records all observed hash-valued attribute layers for the same fixed nine paths. An unknown layer with any service value fails; no precedence is inferred for it. Known normal/default/override projections must agree with the existing typed projection. Automatic/system layers must have those fixed service values absent. The original file names and full configuration never leave the container, and no Cinc or `show-config` call is made.

This is an additive V4 namespace. V1, V2 and V3 source bytes, consumed intents and failures remain immutable and reopenable. Preparation uses a new exclusive private directory. Supervision files remain in a separate sibling. No actual launch is authorized by source preparation alone, and neither a successful cleanup nor a repaired harness promotes historical task/model outcomes. Three complete fresh boots, exact SQL/Git readbacks, typed native settings, strict shutdown, complete absence, restored original state, and independent raw replay are still required before a prospective task amendment is considered.
