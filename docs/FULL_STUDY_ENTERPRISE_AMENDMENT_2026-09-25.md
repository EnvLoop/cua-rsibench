# Enterprise application cell amendment - 2026-09-25

**Status:** pre-result protocol amendment. No official final task or researcher campaign had run when this cell choice was made. The earlier [full-scale implementation plan](plans/2026-09-24-full-scale-computer-use.md) proposed ServiceNow WorkArena. This document preserves that proposal while changing the sixth primary cell to **original Odoo Community** (`odoo-community`) before any final outcomes are observed.

## Why the primary cell changes

The [WorkArena gate audit](evidence/servicenow-workarena-pdi-gate-2026-09-25.md) found the existing gated instance request still awaiting author review. The instance-data usage scope permits benchmarking, evaluation, and research, but not training; no instance or 100-task setup/reset qualification was available. A ServiceNow Personal Developer Instance is a separate original-software development route, but no tenant or high-volume benchmark permission was established, and a full PDI wipe takes hours rather than providing per-task reset. Replacing that missing service with a fake page or silently naming another website “WorkArena” would invalidate the intended result.

The [Odoo Community development gate](evidence/odoo-community-fallback-2026-09-25.md) instead deployed an original, version-pinned Odoo 18.0 application backed by PostgreSQL. It seeded a synthetic purchase-and-inventory world, attached a clearly labeled 112-observation authentic SEC excerpt as reference material, and demonstrated four native-GUI positive controls across two causal workflows, two wrong-object negatives, independent read-only SQL evaluation, and full observed database/filestore restoration. The software and initial data provenance are distinct from ServiceNow and WorkArena; Odoo scores will **never** be called WorkArena scores. Any later approved WorkArena results are a separate supplemental track, with no gated instance data used for model training.

## Additional Odoo qualification gates

The observed Odoo fixture is **not yet an official benchmark cell**. Its current 20/100 RFQ proposal overlaps on vendors, SKUs, and all eight fault patterns; the undeployed 40/20/100 generator proves only a proposed entity-disjoint layout and still shares templates. Before Odoo enters the frozen 4 x 6 final matrix, require all of the following:

1. At least four implemented, causally distinct business workflows with explicit task-family counts and task-level no-regression rules. Supplier-confirmation reconciliation and inventory replenishment are the first two; receipt, invoice/credit, or permission workflows are proposed, not yet implemented.
2. A seeded train/selection/final world split with distinct task IDs, vendor/order/product entities, and source groups; any intended within-template generalization is explicitly declared. Synthetic operational facts and authentic historical SEC reference facts are separate fields and evidence tiers.
3. Exactly 20 selection and 100 final identities whose **individual** fresh-environment GUI positive, plausible negative, saved-state readback, independent verifier, and database-plus-filestore reset receipts pass. Four development positives do not count toward these 100 unless each is independently re-admitted under the frozen final protocol and has no training/public exposure.
4. A fixed Qwen3.8 screenshot/action/renderer contract, task-time/call budgets, evaluator-only gold, application/image/source hashes, and verified rights for all released materials. Only evaluator-owned setup and scoring may use Odoo XML-RPC or SQL; the student actor must use the native GUI.

Until these gates pass, the Odoo cell is `provisional_unqualified`, the full matrix remains blocked, and the publication report retains **0/24 campaigns and 0/600 official final identities**. This amendment establishes the cell's name and acceptance rule; it does not manufacture a score or guarantee that the Odoo candidate pool will yield 100 qualified tasks.
