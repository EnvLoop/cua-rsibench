# Original Magento sample-catalog candidate inventory

Checked 2026-09-25. [`export_magento_catalog_inventory_v1.py`](../../tools/export_magento_catalog_inventory_v1.py) opened a read-only SQL transaction in the pinned loopback Magento Open Source 2.4.6 smoke image and read configurable parent/child SKUs and default prices. It did not alter the shared container. The private inventory is SHA-256 `742f505a16bdc9e478c2af2414455e50530ad824878c20254204314ccc5056cf`. It contains 147 configurable parent families, 145 eligible after excluding one public training-development family, and 115 with at least ten variants. These are sample-catalog entities, **not real retailer sales or customers**.

The deterministic private-seed [candidate planner](../../magento_catalog_factory/plan.py) generated **20 train, 20 selection, and 100 final candidate** identities using disjoint parent families. The final 100 have one source family per parent and 25 each of four five-variant causal pricing policies; all 500 target prices differ from the respective starting values. Supplier quote-page content, SKU-level facts, and planned target prices are generated privately. A saved-state verifier is implemented but has not yet been calibrated on an original candidate. The task instruction directs the actor to read the quote in Content > Pages and save the derived prices through Catalog. The same private seed and source snapshot regenerate identical package hashes. The selection/final/source/template/instance split passed the offline `scale_final_v06.validate_splits` structural check; this check does **not** establish that Magento GUI saves, reset, rights, or model behavior work on those IDs.

The [public receipt](magento-original-catalog-100-candidates-2026-09-25.json) binds the ignored private source inventory, seed, and candidate plan without exposing task text, quote facts, product IDs, or gold. A train-only quote page has been installed in a disposable clone, but **0/100 final candidates have a task-specific GUI positive/negative/reset calibration, 0/100 are officially admitted, and no model has been scored**. The published WebArena-Verified task controls remain development comparators, not scores on this new hidden cohort.

A [trusted quote-page seeder](../../magento_catalog_factory/seed.py) and [saved-state verifier](../../magento_catalog_factory/verify.py) are now implemented for a dedicated no-mount Magento clone. The verifier reads exact target/comparator prices, the seeded CMS source, nine catalog tables, seven unrelated business tables, and the search index; it rejects partial prices and collateral changes. The PHP read path was exercised without writes against the pinned shared smoke image, and focused synthetic positive/negative tests passed. One train-only original case has now been seeded and subjected to a failed strict GUI positive; this does not calibrate any final candidate.

The [clone preparation](../../tools/start_magento_original_clone_v1.py) and [one-case GUI control](../../tools/qualify_magento_original_catalog_v1.py) have been run for the train-only case below. The GUI control deliberately leaves its disposable clone mutated; a separately evidenced fresh-clone reset and task-specific positive/negative controls are still required for every candidate before any final admission.

The [fresh-clone reset auditor](../../tools/audit_magento_original_fresh_reset_v1.py) requires distinct container identities, the same pinned no-mount image and ports, identical task package/quote bindings, and exact equality of the independently read monitored SQL and product-search state. The fixture seeder fixes the synthetic quote creation timestamp so this equality is meaningful across clones. This auditor has unit tests but no original-candidate live reset receipt yet.

A first **train-only** original task was seeded in a separate, mount-free clone. The native CMS page displayed the quote after expanding its Content section, and a scripted GUI edit saved the one named variant at its planned price. Independent SQL confirmed that target price and all unrelated catalog/business/search hashes, but the strict verifier rejected the attempt because Magento's native product save also changed several other fields on that target. A read-only comparison with the pinned catalog baseline found newly materialized product attributes, description newline normalization, index updates, and changed target stock policy fields including `manage_stock`; the stock change is substantive and cannot be silently ignored. The private before/after state, field-level diff, and masked screenshots are retained; the clone was stopped and removed before a fresh baseline comparison. Earlier GUI-driver errors occurred before any product save and each had exact monitored baseline equality. This is a failed strict development positive, **not** an admitted task or model score. A task fixture may need neutral native-save normalization before its frozen baseline; that path needs its own GUI, verifier and cold-reset controls.

A second fresh clone began with the same monitored SQL/search state as the first clone before any actor action, when compared under the original snapshot schema. Trusted setup then performed a **neutral native GUI save at the unchanged starting price**. The target price, source page, unrelated catalog rows, seven business-table hashes and unrelated search documents stayed unchanged; target product defaults were normalized. A subsequent scripted price edit through the native GUI scored **1.0** by the independent saved-state verifier against that normalized baseline. These controls are train-only development evidence, not final-task admissions.

A third fresh clone reproduced the same neutral-save business/search state. Its only cross-clone difference was the target product's automatic `updated_at`; [trusted finalization](../../tools/finalize_magento_normalized_baseline_v1.py) fixed that field to a declared timestamp and verified that no other field, source, price, business table, or search document changed. From that frozen normalized baseline, a GUI edit of a plausible wrong variant scored **0.0** with the target unchanged. The wrong-variant control began from exactly the saved frozen baseline and the clone was subsequently removed. One further independent clone must reproduce the frozen baseline bytewise before the train-only development trio can claim a complete fresh-reset control. These controls still confer **no** official final admission.

The fourth disposable clone failed **before task seeding**: on this ARM host, its pinned x86 Elasticsearch startup did not expose port 9200 within the bounded search-health window, including one isolated restart. The container was stopped and retained for inspection; this is an environment-startup failure, not a model outcome or a failed benchmark task. A bounded alternate-host probe used [E2B's documented custom-image template path](https://changelog.e2b.dev/resources/introducing-build-system-2-0) with the same pinned public image. Three E2B builds returned `BuildException` during template provisioning, before sandbox creation or GUI execution; the final instrumented build log is privately retained under SHA-256 `857beaba9b81e85f70f74fd50c22420d7e7855249d142f9a36e5e1f56f9e92d8`. The provisioning tail reports one package-installation error without the failing package or a successful custom template. The account's actual build charge remains unverified.
