## Reclassified task outcomes

The first queue had 100 candidates in 33 intent-template families: 66 records labeled `mutate`, 29 `retrieve`, and five `navigate`. The published `AgentResponseEvaluator` expects `ACTION_NOT_ALLOWED_ERROR` for **two** of the 66 mutation-labeled records, task IDs **491** and **790**. Neither has a `NetworkEventEvaluator`; a correct response does not save the requested change. They can be useful policy-denial tests, but they cannot enter a cohort of successful saved-state mutations. The manifest's blanket `network_only_for_mutation=true` and `requires_saved_state_oracle=true` flags therefore misclassify these two records. The 20-case selection set also contains two `NOT_FOUND_ERROR` retrieval cases; its status mix is 18 `SUCCESS` and two `NOT_FOUND_ERROR`.

## One inconsistent published network assertion

Task **423**, a product on-sale mutation, is labeled `SUCCESS`. Its current network evaluator targets a Magento `/catalog/product/save/...` URL with response status 302, but asks the request body to contain `report_type=created_at_order`, `from=02/1/2023`, and `to=02/28/2023`; it does not specify an HTTP method. Those report-filter fields do not describe the requested product sale-status change. The same pinned checkout's original `assets/dataset/test.raw.json` task 423 instead checks the rendered product-sale field for value `1`. This is a concrete source/evaluator inconsistency, **not proof that the task is impossible**: a native GUI attempt, captured request, saved product-state readback, plausible wrong-object negative, and reset are required before retaining or correcting this task. Do not weaken an evaluator merely to make a failing candidate pass.

Among the other 63 successful-mutation candidates, every published network assertion specifies `http_method=POST`; the inconsistent task 423 is the sole successful-mutation candidate with a network assertion that omits the method. The two policy-denial cases have no network assertion. The 29 retrieval candidates likewise have no network assertions, so their official scores alone cannot prove browsing provenance. The five navigation candidates each have one network assertion; two report-navigation tasks use the same report UI family as selection tasks under a different `intent_template_id`. Template separation is therefore not a claim of distinct user-interface workflows.

## Leakage and solvability boundary

The audited first selection and final queues were disjoint on task ID and `intent_template_id`. The planner reserves 25 source records from five selection template families, uses 20, and excludes eight other records whose explicit source-entity hint equals one of those reserved-family hints. This audit found no additional exact overlap of nontrivial scalar `instantiation_dict` values across the chosen 20/100 records, and no cross-split reuse among the product, order, address, review, or attribute IDs explicitly present in evaluated URLs or start URLs. Those negative findings cover only visible fields. They cannot rule out shared customers, products, orders, reviews, or other database rows reached by different queries and templates. The published task file also contains instructions and evaluator answers, so this queue cannot be called a sealed final exam even if the generated JSON is withheld.

The status-aware reclassification and task-specific quarantine are now implemented in the planner. The next admission gate is to recheck entity-level overlap for the rebuilt queue against the seeded Magento database and validate task 423 through the specified GUI/SQL/HAR control. For each candidate, verify one visible-GUI positive and a plausible negative, the expected saved state or answer provenance, unrelated-state preservation, and reset-to-baseline. Until then the official-final admitted count is **zero**.
