# Pinned-border physical-dispatch profile

The second original Odoo selection control stopped after a durable step-8
intent because six physical screenshots remained at one two-pixel variant of
the model-visible frame. The [independent incident audit](odoo-v066-selection-second-post-intent-stale-2026-09-29.json)
shows no step-8 mouse dispatch, exact saved SQL/full-filestore reset, and two
retained failed attempts. Both prior attempts remain terminal.

This dated **new** physical-dispatch profile keeps parsing bound to the exact
model-visible screenshot and the unchanged v0.6.6 action validator. It is an
explicit Odoo exception to byte-exact physical-frame equality at dispatch;
it must not be reported as an unchanged strict exact-frame result. At
dispatch it first tries the exact-frame-return guard. If that fails, the
only allowed alternate is one recurring PNG that differs at precisely
`(41, 419)` and `(132, 419)`, with RGB `(235, 237, 239)` ↔
`(235, 237, 240)`. All six bounded dispatch samples must be that same
alternate. URL, task identity, and frame ID stay bound; any third image or
material pixel difference fails closed. Equivalence is allowed only for a
visible, enabled click, double-click, or type target whose current Odoo
control ref, role, label, visibility, and enabled state match the controls
saved in the model-visible payload and immutable action intent. Its bounds
and target point must exclude both changed border pixels. The exception is
restricted to the native Purchase/RFQ form and this purchase-family case;
other Odoo views continue to require exact physical frames.

Each successful dispatch receipt now states whether the physical frame was
exact or used the pinned-border exception, and retains the physical PNG hash,
frame ID hash, target-control readback, and fixed pixel coordinates. The
independent auditor reopens every sampled PNG and recomputes the pixels,
sample order, receipt binding, and target disjointness. A final physical PNG
is captured after the target DOM readback and immediately before the mouse
action; it must still be the same pinned alternate. The journal in this
profile binds each event to the immutable batch-intent SHA-256, so distinct
runs cannot share an identical journal payload as the two failed attempts did.

A third same-ID selection attempt is **not** authorized by the old gate. A
fresh no-GUI preflight must audit both retained failures and query the
current SQL and full physical filestore under the original worker lease.
Only exact agreement with the frozen baseline and restored stopped services
can write a new private gate. The third run then verifies that gate and the
unchanged worker-lease prefix before `case_started`. It uses a fresh run
directory and permits one bounded GUI case under explicit execution flags;
there is no automatic replay.

The [RFQ-view source freeze](odoo-v066-scale-pinned-border-rfq-view-source-freeze-2026-09-29.json)
and field-limited [selection](odoo-v066-selection-control-plan-pinned-border-rfq-view-2026-09-29.json)
and [hidden](odoo-v066-official_hidden-control-plan-pinned-border-rfq-view-2026-09-29.json)
plans bind this proposed lane. No third GUI attempt, hidden task, model call,
or official final admission is yet claimed. Hidden dispatch remains on hold
until a fresh selection case passes independent saved-state and visual review.
The earlier pinned-border and observation-bound freezes remain preserved
pre-dispatch drafts.
