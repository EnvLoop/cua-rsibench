# PowerPoint web fresh-copy download and artifact-readback gate

This addendum advances the [local fresh-copy controller](office-web-fresh-copy-reset-gate-2026-09-25.md) but does **not** admit an Office benchmark task. A live operator used the dedicated benchmark account in the in-app browser to create one new PowerPoint web copy from the development control deck. The UI presented a “Download a copy” flow with a separate final **Download** button. That final button was clicked twice. No browser download event was returned, and a subsequent check found no corresponding PPTX in the normal Downloads location, the Codex app support files, or the task temporary directory. There is therefore no artifact that an independent verifier can bind to the cloud item or score. The cloud URL, account identifiers, and filenames remain evaluator-private. The earlier wrong-account Chrome terms screen was not accepted or used.

The new offline [`audit_office_web_fresh_ppt.py`](../../tools/audit_office_web_fresh_ppt.py) freezes the target size, target shape, source package hash, and expected collateral part **before any downloaded artifact is bound**. It then requires five separate local artifacts: untouched, full positive, mixed-title partial negative, target-correct collateral negative, and fresh reset. The evaluator compares every OOXML package member against the frozen Office-normalized baseline. Only narrow, previously observed Office save metadata is ignored; title run size is the sole allowed target mutation. The partial control needs both correct-size and noncorrect-size title runs. A reset artifact must return to baseline package semantics. Missing, corrupt, changed, or prematurely bound artifacts fail or remain incomplete. Even a passing artifact audit reports `gui_admitted: false` until a reviewer independently verifies UI action traces, cloud-item isolation, save/reload, and true fresh-copy reset provenance.

The oracle froze successfully against the actual Office-normalized 32-slide PPT-Eval development baseline, whose published SHA-256 remains `71a06838dfe24595aa39ab6c0c7bdaeed127ea78079a94323de99c28b30029cd`. It has **zero bound downloaded files**; the real browser copy cannot pass the artifact audit yet. Synthetic test decks exercised a full positive, a mixed partial edit, collateral slide and media changes, missing downloads, a changed oracle, and a corrupt file; 23 related tests passed. These tests establish the verifier's behavior, not Microsoft web execution.

The supported computer-use interface exposes UI clicks and accessibility/screenshot observations, but no file download event or local output path for this in-app browser session. The current browser path therefore stops after the visible download confirmation. A future run can bind a file from the browser's ordinary download UI or a dedicated-account system-browser session if that file is visibly obtained and its origin is independently checked; neither path was verified here. Raw browser protocol inspection is not part of the admission evidence.

**Observed cell status:** one additional online development copy, zero new local cloud downloads, zero fresh-copy positive/negative/reset artifact controls, zero new GUI admissions, zero official final-task credits, and zero model calls.
