The source count clears an **arithmetic** 20-selection/100-final gate with whole-family separation: four of the 27 five-ID families could supply 20 selection IDs, and 20 of the remaining 23 five-ID families could supply 100 final candidates. This is a capacity proof, not an admitted task list. Status, difficulty, saved-state behavior, source-entity overlap, and authentic GUI solvability can reduce the usable pool; replacements must pass their own controls.

## Source and evaluator risks

- **Quarantine task 102.** Its instruction and `instantiation_dict` identify the `a11yproject/a11yproject.com` project, while both network assertions target `byteblaze/a11y-syntax-highlighting`. The other tasks in its template family do not show this project mismatch. A passing network trace for task 102 would therefore not establish the requested destination. This is a source/evaluator inconsistency, not proof that the GUI task is impossible; any repair needs visible-GUI and independent final-page evidence.
- The source's navigation checks observe requests, not the final rendered page. Tasks 45 and 46 ask for the most recent open issues, but each accepts a plain project issues-page URL without explicit sort or state parameters. This may coincide with the application's defaults, but the published assertion alone does not prove the filter.
- For successful mutation tasks, 134 of 171 network assertions constrain request-body data. The remaining 37 are the star/follow families: 21 star-toggle assertions across five tasks and 16 follow assertions across five tasks. Their URLs, response content/status, and method provide useful evidence, but saved-state readback is still required, especially for a toggle. The five star tasks have nested target sets; the five follow tasks reuse several accounts. These variants must run from a restored baseline.
- Template disjointness does not prove entity or workflow disjointness. Tasks 660 and 670 use different template IDs but the same `byteblaze/dotfiles` project. Templates 332 and 2100 describe closely related private-project creation plus membership workflows. The local source fields do not establish independence of seeded issues, projects, users, or database rows across an eventual split.

The existing [task 590 milestone probe](gitlab-milestone-mutation-2026-09-24.md) demonstrates one deterministic visible-UI, PostgreSQL, wrong-date, and reset control on a **synthetic fixture**, not on the original populated WebArena GitLab seed. This new audit admits **zero additional GUI tasks** and **zero official final GitLab task identities**. A real 20/100 queue still needs a frozen, status-aware and entity-aware split; each selected family needs visible-GUI positive and plausible negative attempts, an independent persisted-state or retrieval oracle, no-regression checks, and a restore-to-baseline proof. The public source tasks can serve qualification and calibration while a genuinely hidden final exam requires separately controlled task content and evaluator answers.
