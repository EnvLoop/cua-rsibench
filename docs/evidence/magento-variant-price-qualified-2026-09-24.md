# Magento five-variant price task: qualified after clone repair

This is a **single scripted GUI qualification**, not a model result or an official final-set attempt. It follows the immutable [rejected attempt](magento-variant-price-rejection-2026-09-24.md) for [WebArena-Verified task 777](https://github.com/ServiceNow/webarena-verified/blob/6473f72db5dcefc97b5725b59e734504edc28a21/assets/dataset/webarena-verified.json). The task asks for a $5 reduction in all five green size variants of one sweatshirt. The exact pinned task, source, image, evaluator, and tool hashes are in the [field-limited qualification receipt](magento-variant-price-qualified-2026-09-24.json).

The test used one disposable, mount-free Magento 2.4.6 clone, exposed only on loopback ports 7792/7793. Its first search process stayed in JVM bootstrap for several minutes and had no listener on port 9200. Restarting **only that clone's** Elasticsearch process brought one data node to HTTP 200 with yellow health and no pending tasks. The image also redirected `/admin` to its baked `localhost:7780`, which belongs to a different container. The clone's own Magento base URL was changed to `http://localhost:7792/` and its config cache cleaned before GUI use. A pre-repair GUI probe timed out before login and made no product edits. The shared Magento smoke container was not changed.

The [scripted oracle](../../tools/qualify_magento_variant_price_v1.py) then used a fresh Chromium context and the visible Magento admin UI. It searched each SKU, opened the matching product, checked the visible SKU and initial $52 price, entered $47, clicked **Save**, and waited for **“You saved the product.”** The [positive screenshot](magento-variant-price-qualified-positive-2026-09-24.png) shows the confirmation for the last green size; the [wrong-color screenshot](magento-variant-price-qualified-negative-2026-09-24.png) shows the same native save on the red XS control. Account identity is masked in both images. No model was called.

| Case | Independent persisted-state readback | Unchanged published evaluator | After-case reset |
| --- | --- | ---: | --- |
| Five green sizes | Product IDs 111, 114, 117, 120, 123 each changed from $52 to $47; red XS stayed $52 | 1.0 | Monitored SQL rows and all 181 product-search documents matched baseline |
| Wrong-color red XS | Product ID 112 changed from $52 to $47; all five green sizes stayed $52 | 0.0 | Same SQL and complete search-index baseline match |

The published evaluator produced the same scores on the raw private HAR and a sanitized, price-field-only HAR. Neither HAR nor browser authentication state was published. Independent SQL readback covered nine product, EAV, stock, and price-index tables. The SQL restore alone was insufficient: after the first successful run, the search index still showed the configurable parent at $47 while SQL had returned to $52. The strengthened tool therefore reindexes `catalogsearch_fulltext` from restored SQL after each case and compares the canonical contents of **all 181 search documents** with the prepared clone's pre-task snapshot. Its baseline SHA-256 was `54ca1d8ef5cb82ed879338e6740a589a930e50cd8a54f495c234c5f5b0acf6fb`; both post-reset digests matched it. The target parent indexed price also returned from $47 to $52. Final monitored-state reset passed.

The original rejection remains correct for its earlier failing clone: HTTP 302 and a network-only score of 1.0 did not prove a save there. This repaired run qualifies **one** task in **one** clone under a stronger verifier. It does not prove arbitrary Magento reset, a 100-task-ready population, hidden-set isolation, or improvement by Qwen. The seven focused qualification tests pass.
