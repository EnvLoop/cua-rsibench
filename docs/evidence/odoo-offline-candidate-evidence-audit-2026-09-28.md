# Odoo candidate evidence: source-bound offline re-audit

The [machine-readable receipt](odoo-offline-candidate-evidence-audit-2026-09-28.json) and a mode-0600 evaluator-private per-ID report recheck the historical Odoo Community 18.0 controls without starting Docker, opening a browser, or calling a model provider. The audit rebuilt the source asset and task-package bytes for all **20 train, 20 selection, and 100 hidden-candidate** identities under the pinned historical Odoo source. It reopened each GUI run receipt and checked the unsolved baseline, source visibility, persisted positive result, wrong-object negative, exact cold reset, nonoverlapping exclusive worker interval, and matching public receipt and checkpoint hashes. Cross-split task, package, source, template, and instance identities did not overlap. The public receipt binds the private per-ID report by SHA-256 without publishing IDs, prompts, source values, gold, credentials, or local paths.

This is a re-audit of **historical evaluator controls**, not a new live v0.6.6 GUI/model test. The present actor ACL and SQL privileges were not queried, and neither a researcher campaign nor a hidden model attempt ran. **Official final tasks admitted: 0/100 for Odoo.** The six-cell pre-campaign witness, current live action/runtime acceptance, task-bound model attempts, and billing reconciliation still have to be established separately.

The read-only privacy inventory found **15 directories with mode 0755 and 39 files with mode 0644** inside the three retained private trees: train 8/23, selection 3/8, hidden candidate 4/8 (directories/files). The selection private root is already 0700, but some descendants are permissive. The receipt therefore marks owner-only permissions false and keeps pre-campaign admission closed. No file mode or evidence byte was changed by this audit.

The Odoo Compose definition mounts named database and filestore volumes, not these host-side private directories. A mode-only hardening pass should first confirm that no worker lease or task is active, snapshot the affected paths' modes and hashes, then set private directories to 0700 and files to 0600 as the owning host user. Re-run this offline audit and the worker's read-only file-access checks afterward. Since `chmod` does not alter file content, existing SHA-256 evidence should remain stable; any mismatch or lost host-worker access must stop admission and be investigated. Subsequent live attempts must create owner-only outputs from the start.
