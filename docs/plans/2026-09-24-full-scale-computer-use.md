# Full-scale computer-use Data study implementation plan

**Goal:** Run a new matched four-researcher by six-application study with 100 scored final instances per application, then publish an English report derived only from admitted results.

**Architecture:** Each application supplies an immutable task inventory, reset operation, visible observation/action adapter, and an evaluator-owned saved-state verifier. A shared controller owns four researcher campaigns per application, fixed teacher and student identities, Tinker training, budget accounting, checkpoint selection, remote execution, artifact hashing, and the final report. The completed v0.5 study stays immutable and outside this matrix.

**Technology:** Python 3.12, Tinker LoRA and sampling, Harbor, E2B, application-native test runners, Playwright/browser or desktop screenshots, SQLite/OOXML/application-state readback, signed source manifests, and local unit tests.

The first scale inventory is `work/scale-up-source-manifest.json`; `tools/plan_factory_scale.py` produces an offline workload and budget projection. These are preparation artifacts, not executed scores. This plan uses one official execution per task, matching the main reference's usual shape; any extra repetition is a separately declared stability experiment. Source tasks may be reused for selection and official evaluation only when the protocol declares that choice and creates fresh environments. Evaluation artifacts may guide diagnosis but may not become training supervision. A source-disjoint and template-disjoint transfer set will be reported separately when available.

## Declared matrix

Four researcher configurations: `gpt-6-astra`, `gpt-5.6-sol`, `gpt-6-sol`, and `gpt-6-luna`. Within a cell they receive the same prompt, training sources, baseline diagnostics, student, teacher, action space, tasks, budget, and execution platform. The fixed rollout teacher remains `gpt-5.6-sol`. At the user's direction, the new study uses **`Qwen/Qwen3.8-27B`** as its student. Historical Qwen3.5-4B results remain in v0.5. The 27B model's image-input training and sampling must pass an authenticated smoke before screenshot cells can be frozen. Researcher model IDs remain provider-reported identifiers, not weight attestations.

Six proposed real-software cells are PowerPoint Online, Excel for the web, native desktop applications, ServiceNow, GitLab, and Magento administration. The last two use separate WebArena Verified application domains. Existing source inventories contain at least 100 candidate tasks per cell, but no cell is yet counted as runnable. [Microsoft confirms](https://support.microsoft.com/en-us/accounts-billing/subscriptions/what-s-the-difference-between-a-microsoft-365-subscription-and-free-web-apps) the web versions of Excel and PowerPoint are free with a personal account and include 5 GB of OneDrive storage; this does not prove bulk benchmark entitlement or that every dataset task works in the browser. We admit only Excel tasks with observed GUI editing, saving, recalculation where needed, and independent workbook readback. Unsupported desktop-only tasks are recorded in a separate desktop track. A code-only or API-only success does not satisfy a web-GUI task contract. Real application software is distinct from the provenance of its benchmark content. Every field and artifact records whether it is public historical, anonymized historical, synthetic, or unknown.

Shopping storefront, Postmill forum, and Map are additional WebArena Verified candidates with 187, 106, and 109 single-site IDs. Their 48, 21, and 29 intent templates, weak retrieval/map navigation checks, and untested full resets prevent an automatic substitution for ServiceNow or native desktop. The [single-site source audit](../evidence/webarena-verified-single-site-audit-2026-09-24.md) records the exact limits. WorkArena's published setup requires access to gated ServiceNow instances; this cell remains pending approved access rather than being silently relabeled as another website.

Each cell has 100 frozen official task identities and a proposed 20-task selection set, shared across its four researchers. The 20-task default keeps the 100-task final scale while fitting 120- to 200-task published source pools; it is a protocol choice, not a claim that all 20 are qualified. Training examples require an independently sourced and isolated pool, especially for PowerPoint's exact 20/100 deck split. One research lineage per researcher and cell gives 24 campaigns. Nominal caps per campaign are 16 hours and $500 Tinker cost, with a separate ledger for E2B, researcher and teacher inference, storage, and any licensed application services. The nominal Tinker ceiling across 24 campaigns is $12,000; it is a cap, not a forecast or total bill. The user authorized the full run. The controller stops a campaign at its actual quota or failure boundary and does not convert incomplete work into zero scores.

## Stage 1: make every source inventory testable

1. Pin upstream source commits, asset hashes, licenses, 100 official IDs and their source/instance/template clusters. Keep only identity metadata in the researcher-facing manifest. Preserve existing source records and benchmark answers in evaluator storage.
2. For each application, create one disposable environment, inject one task, complete a known-positive action sequence using the actual GUI, read the saved artifact or application state, score with an independent verifier, and reset. Repeat a negative case that edits the wrong object or leaves an unrelated side effect. A source's published task count does not satisfy this gate.
3. Freeze the set of 100 only after all tasks build, reset, execute, and verify. Exclude structurally ambiguous or unsolvable tasks before researchers see selection feedback. Report source-cluster counts so 100 variations from a few files are not presented as 100 independent worlds.
4. Separate identity and permission tracks: use the dedicated benchmark Microsoft account and OneDrive area for PowerPoint/Excel web, a dedicated ServiceNow instance if access permits, and isolated self-hosted GitLab/Magento. Never use a personal document library as a silent benchmark workspace. On 2026-09-24, both Microsoft web apps opened under the dedicated account. One source PowerPoint task and two constructed SEC Excel development tasks have now passed narrow human GUI save/reload/download and independent OOXML-readback controls. Same-file manual rollback was observed for the PPT task and the newer retail Excel task. Automated fresh-attempt cloud reset, task-family coverage, and model execution remain unqualified. The account and any OneDrive edit links remain private as specified in `docs/ACCOUNT_BOUNDARY.md`.

## Stage 2: version the common computer-use student interface

1. Add a new observation envelope carrying task instruction, visible accessibility/DOM text where available, screenshot bytes, prior action result, and bounded memory. Record exactly which modalities each cell provides. Preserve the v0.5 Kanboard text-only contract unchanged.
2. Add one action envelope for click, type/fill, keypress, scroll, drag, wait, and finish with coordinate/control-reference modes. Validate bounds and current-state references before dispatch. Native runners may translate this envelope into their application actions, but direct API, shell, or file editing is a separately scored track.
3. Validate Qwen3.8-27B image-plus-text rendering, Tinker LoRA training and checkpoint sampling on one disposable visual task. Bind the same renderer and screenshot preprocessing at training and evaluation. A text-only fallback is labeled as a different protocol.
4. Normalize adapter errors into `model_failure`, `verifier_failure`, `environment_failure`, and `transport_or_provider_failure`; only valid task results enter success denominators. Keep raw state and checksum evidence for every action and cleanup.

## Stage 3: replace fixed-size pilot execution assumptions

1. Generalize the final plan from six tasks/two three-task chunks to manifest-defined task sets and tail chunks. Bind task package, student checkpoint, source snapshot, app/runtime version, action contract, verifier version, sampling, and seed before dispatch.
2. Use durable job IDs, pre-dispatch intent, single remote child per chunk, archive/member hash verification, and exact cleanup readback. An uncertain create or execution response is reconciled; a new output directory is not a retry.
3. Add a global concurrency and spend controller. Preflight expected E2B occupancy and API call limits, reserve Tinker cost per candidate, and charge observed usage separately. A provider plan's advertised concurrency is not account-specific entitlement evidence.
4. Run the 100-task base once per application and share that exact evidence across the four researcher comparisons in the same cell. Train/evaluate researcher candidates within each campaign budget. Freeze selections before the official run. Matching is per application; no cross-application pooled ranking without a predeclared statistic.

## Stage 4: execute and publish

1. Complete all six application smoke gates, then freeze one versioned matrix manifest. A cell still lacking login, license, reset, verifier, or multimodal support remains `blocked`, never `completed`.
2. Dispatch 24 campaigns under the same per-cell settings. Retain every rejected dataset, trained checkpoint, scored result, timeout, cost receipt, and complete provider/transport failure. Stop at budget rather than extending a weak run by hand.
3. Run all 100 official task instances for each selected checkpoint and the matched base. Rerun only a separately predeclared infrastructure-invalid suite with original outcomes preserved. Do not relabel that rerun as an extra independent sample.
4. Produce cell-specific success rates, denominator and failure counts, first-to-best candidate changes, peak preservation, actual resource use, and uncertainty across research seeds if new seeds are run. Discuss source/template overlap and account/platform differences.
5. Render an English PDF, figures, and explorer from audited evidence, visually inspect every page, verify site behavior and privacy scans, publish under EnvLoop, and fetch the public assets back for hash verification. The public report cites RSIBench-Data once and describes task families briefly. New result cells remain absent until their runs pass the audit.
