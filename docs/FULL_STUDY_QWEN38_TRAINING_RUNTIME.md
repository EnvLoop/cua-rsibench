# Pinned Qwen3.8 vision training runtime

The 24-campaign study needs a dedicated CPython 3.14.7, macOS arm64 training environment. The general project venv has Transformers 5.17.0, while the frozen `tinker-cookbook` revision permits at most 5.5.4. A temporary `PYTHONPATH` overlay proved that a one-step toy Tinker call could run with Transformers 5.5.4 and tokenizers 0.22.2; it is not an acceptable campaign runtime because it mixes package trees from two environments.

The [hash-locked wheels](../runtime/qwen38-vision/requirements.lock) pin Tinker 0.30.0, Transformers 5.5.4, tokenizers 0.22.2, `tml-renderers` 0.1.0, Torch 2.13.0 and their resolved dependencies. The cookbook is installed separately from the clean Git checkout at `1e53aa3d1cdd6389b3290c2574641eccc0503242`, using the lock's Hatch build tools with build isolation disabled. The [runtime snapshot](../runtime/qwen38-vision/runtime-spec.json) binds the Python/platform identity, both requirement files, the cookbook commit and tree, all 86 installed distribution versions with `METADATA` and relocation-normalized `RECORD` digests, source trees for the five critical rendering/provider packages, repository renderer/training source files, processor configuration, tokenizer vocabulary, and one offline image-bearing SFT/sampling render. The [verifier](../tools/verify_qwen38_training_runtime_v1.py) checks each installed file against its own `RECORD` hash and size before computing the portable digest. It makes zero provider calls.

The first isolated venv and the later durable-root rebuild had identical versions, metadata and critical package trees but different raw `RECORD` hashes in 20 distributions. The only changed entries were 26 generated console scripts: their first line contains the absolute venv path. The verifier now requires that each such file's original bytes match its installation-specific `RECORD`, requires the exact expected venv shebang, and hashes the same script again with only that checked line replaced by a fixed placeholder. All other `RECORD` entries retain their original hash and size. It also verifies every installed file named by a hash-bearing `RECORD` row. This makes a clean reinstall at a different path comparable while still rejecting a changed launcher body or package file. The durable-root rebuilt venv passed the amended offline verifier against the same runtime-spec SHA as the isolated venv.

Rebuild this runtime in the durable **root study checkout** before campaign dispatch. The venv used to prepare this evidence is an ignored directory in an isolated Codex worktree; its path is not a published runtime and must not be reused after that worktree is retired. With a clean local cookbook checkout at the commit above and a CPython 3.14.7 executable available:

```bash
uv venv work/qwen38-training-runtime/.venv --python /path/to/python3.14.7 --no-project
uv pip sync --python work/qwen38-training-runtime/.venv/bin/python --require-hashes runtime/qwen38-vision/requirements.lock
uv pip install --python work/qwen38-training-runtime/.venv/bin/python --no-deps --no-build-isolation /path/to/tinker-cookbook-pinned
uv pip check --python work/qwen38-training-runtime/.venv/bin/python
PYTHONPATH=src work/qwen38-training-runtime/.venv/bin/python tools/verify_qwen38_training_runtime_v1.py --cookbook-dir /path/to/tinker-cookbook-pinned
```

The cookbook checkout must be clean and its Git HEAD must match the pinned commit. The verifier runs with Hugging Face and Transformers offline, constructs the same Qwen renderer used by the benchmark, checks an `ImageChunk` in supervised and sampling inputs, and checks positive assistant loss weight. It does not load provider weights, open a Tinker client, train, sample, or inspect benchmark task gold. The hash-locked wheels plus the separately built cookbook were resolved and installed on macOS arm64; wheel availability and byte-for-byte installed metadata on another OS, architecture or Python patch version are unverified. A different platform needs a separate lock, runtime snapshot and offline validation before any paid campaign call. Keep this model stack in a separate process from the general test runner: a mixed test process has reported duplicate `libomp` loading after adding the Tinker dependencies. The process boundary and dedicated venv are the supported isolation; `KMP_DUPLICATE_LIB_OK` is not used.

The [field-limited toy evidence](evidence/tinker-qwen38-vision-clean-runtime-2026-09-28.md) keeps two observations separate: a paid one-step toy train/sample operation performed under the temporary compatible overlay, and a later **offline** renderer/SFT probe in the clean dedicated venv. A separate read-only checkpoint lookup reported `Qwen/Qwen3.8-27B` as the toy checkpoint's base model and made no new training or sampling call. Neither observation is a real GUI episode, selected checkpoint, 20-task selection score, final result, weight-byte attestation, or proof that the 24 campaigns can complete. Actual provider invoice USD remains unknown. The [pre-dispatch gate](FULL_STUDY_QWEN38_PRE_DISPATCH_GATE.md) is now wired into both campaign and shared-base Tinker paid-call boundaries, and requires the actual worker to run from the verified dedicated runtime. This runtime snapshot alone grants no dispatch authority: the authentic six-cell freeze, task qualification, provider budget and usage evidence remain required.
