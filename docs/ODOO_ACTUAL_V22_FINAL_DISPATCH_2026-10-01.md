# Odoo actual V22 final dispatch

This additive worker uses the current V13 native actor, independent SQL and
physical-file scorer, exact reset, native guard and typed 720-second actor
clock. It leaves the 57-file V13 control binding unchanged. Its separate final
source snapshot must be closed before any research campaign. Existing control
proofs qualify the native source only; they do not admit formal model results.

The constructor reads metadata only. `run_once` first checks the real witnessed
V22 FinalGate, all 600 qualified tasks and all 24 completed research chains,
exact 100-task identities, owner, checkpoint hash/path, common runtime/source
snapshot, sampling, private output and the already-dispatched parent paid
reservation. Only then does it open that command's private final task body.
The same worker handles shared base and all four selected checkpoint slots.

Each task owns a fresh sampler and native environment. The actor gets 90 GUI
turns and an absolute 720-second deadline; setup, saved-state readback, exact
reset and acknowledged provider close are measured separately within the
owned 1200-second lifecycle. A typed terminal deadline may retain independently
scored performance only with the reopened V13 budget-performance proof.
Ordinary provider faults and uncertain native I/O do not become scored budget
stops. No consumed request is automatically replayed.

The parent whole-task paid ID is retained. Each frame records the actual Tinker
sampling-journal request ID, durable intent and actual completed result, or a
null result for the checked terminal deadline. Usage and invoice amounts stay
null when the provider has not supplied authentic billing; a nominal quote is
not an observed charge.

## Source preparation (no native or paid call)

Use the imported repository as `$REPO` and its configured Python as `$PY`.

```bash
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH="$REPO:$REPO/src" "$PY" \
  -m tools.odoo_native_surface_final_v22 prepare-source \
  --output-dir "$PRIVATE_STAGE/odoo-v22-final-source.private"
```

This writes private native binding, supplemental final binding and combined
study snapshot. Freeze the combined snapshot's canonical SHA in every Odoo
slot's `source_snapshot`, while retaining the qualified V13 native hash in
`runtime`. The V22 manifest must include the supplemental Python sources and
CLI; no source mutation after campaign freeze is admitted.

## One already-authorized final command

The private execution spec has schema
`odoo-real-v22-final-execution-spec-v1` and exactly these fields:
`qualified_parent`, `amendment_path`, `manifest_path`, `policy_witness_path`,
`final_gate`. The first field contains the actual legacy FrozenStudy constructor
arguments. `final_gate` contains `matrix_manifest_path`,
`prepared_matrix_dir`, `completion_index_path`, `final_public_commit_sha1`,
and `policy_final_witness_path`. The CLI reconstructs real V22 authority; it
accepts neither synthetic fixture authorization nor a declaration-only gate.

The private worker configuration contains exactly `native_worker_module`
(`enterprise_fallback.odoo18.native_surface_workers_v13`),
`native_binding_path`, `native_binding_file_sha256`, `source_binding_path`,
`source_binding_file_sha256`, `worker_dir`, `final_output_root`,
`local_cost_authority_path`, and `local_cost_authority_sha256`. Local cost
metadata remains a nominal estimate. The command is the actual command emitted
and reserved by the real V22 FinalController, not a hand-written paid identity.

```bash
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH="$REPO:$REPO/src" "$PY" \
  -m tools.odoo_native_surface_final_v22 run-once \
  --runtime-spec "$SPEC" --runtime-spec-sha256 "$SPEC_SHA" \
  --worker-config "$CONFIG" --worker-config-sha256 "$CONFIG_SHA" \
  --command "$COMMAND" --command-sha256 "$COMMAND_SHA" \
  --output-dir "$OWNED_ATTEMPT_DIR" --execute
```

Use the worker object from `final_worker_factory` in the actual six-worker
`full_study_final_performance_v2.FinalController` registry. The one-command CLI
is a checked execution endpoint; it does not reserve, admit, settle or publish
a formal result by itself. Unknown billing stays separately unresolved.

## Public TRAIN model pilot boundary

A public TRAIN development pilot should precede the formal campaign. It uses
the exact accepted V13 TRAIN control and current factory/guard, an explicit
root-reviewed public TRAIN task, and genuine paid Tinker/provider intent.
It must not reconstruct a fake 600-task/24-chain gate to run that pilot.
The final worker intentionally cannot serve as that development endpoint.
A separate development-only pilot interface and its private reviewed request
will be supplied before native/model dispatch; no final bodies or formal
admissions are required or permitted for it.
